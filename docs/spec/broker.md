> Part of the RenderEngine spec (see `SPEC.md` for the index). Section numbers
> are stable; references like "SPEC §11" mean this file. This section was added

## 11. `scene/` + `broker/` disposition

### 11.1 Why two libraries

- **`scene/` — app-side scene description, GL-free, RE-free.**
  Folder `scene/` (peer to `io/ data/ volume/ core/ render/ broker/ app/`) is
  the **owning library for every type an `app` author touches**. It replaces the
  prior scattered `app/mpr_slice.hpp` + `render/*_renderer.hpp` `Scene` structs as
  the source of truth for `View`, `Camera`, `PlaneDesc`, the
  `SceneObject` family, `MaterialDesc`/`LightDesc` hierarchies and the
  `SceneStore`/`ViewStore` that carry stable handles + `generation` per object.
  It depends on `data/` + `volume/` + `glm` only.

- **`broker/` — `scene/ → render/` mediation, heavily abstracted per-type
  mappers, plus persistence/caching.**
  Folder `broker/` (peer to `scene/` and `render/`) is the **only** place that
  may include **both** `scene/` and `render/`. It owns no `GL` and no app
  rendering logic — only `IMapper<AppT,ReT>` per-type translation,
  `TransferFunction → uniforms` and `PlaneDesc(Space) → ClipPlane` conversion,
  plus the `generation/contentHash` caches from SPEC §10. `app/` never holds a
  mapper handle; `render/` never includes `scene/`.

### 11.2 Naming — translators have a better name

The per-type translators are **mappers** / **binders** on the broker,
and the façade is a **bridge** / **broker**. Reserved choice for the
implementer's naming pass (pick one, document it; update bulk-references):

| Role | Candidate name | Interface | Status |
|---|---|---|---|
| Per-type `AppT → ReT` translator (pure) | `Mapper<AppT,ReT>` (recommended: `IMapper`) | `Result<ReT> map(const AppT&, const TranslateContext&)` | **Recommended** |
| Cached translator (decorator) | `CachedMapper<AppT,ReT> : IMapper<AppT,ReT>` | `+ Result<ReT> mapCached(const AppT&, const TranslateContext&)` + `void invalidate(Id)` | **Recommended: separate ISP** |
| | `Binder<AppT,ReT>` | `bind(const AppT&) → ReT` | alt — "binding" reads well for `ViewMapper` |
| | `Exchange<AppT,ReT>` | `exchange(const AppT&) → ReT` | alt — matches `translate/` legacy |
| | `Adapter<AppT,ReT>` | GoF `Adapter` | alt — but GoF Adapter is interface conversion, not sync caching |
| | `Converter` | `convert` | alt — too generic, hides caching |
| | `Synchronizer` | `sync` | alt — but sync is the bridge's word |
| Registry | `Broker` (recommended) / `MapperRegistry` / `ExchangeRegistry` | `template<AppT,ReT> IMapper<AppT,ReT>* get()` + factory `registerMapper(make_unique<Mapper>)` | **Recommended: `Broker`** |
| Façade that app touches | `ViewBridge` (recommended) / `SceneBroker` / `Bridge` | `sync(appViews, sceneStore)` → `renderAll()` → `presentAll(dst)` via composed collaborators | **Recommended: `ViewBridge`** |
| Per-type concrete | `{MeshObject,VolumeSliceObject,PlaneObject,Material, …}Mapper` | one file per type (`broker/mesh_object_mapper.*`) | required: one file per type (guardrail) |

App code path uses **only** the façade (DIP: `app` depends on `IViewBridge` abstraction, not concrete `ViewBridge`):
`IViewBridge& bridge = appContext.viewBridge(); bridge.sync(appViews, sceneStore); bridge.renderAll(); bridge.presentAll(nullptr);`
App never calls `CameraMapper` etc. directly.

**SOLID 11.2.1 — ISP segregation (research-backed, web-verified 2026-08-23):** The single `IMapper` with `map`+`mapCached`+`invalidate` is a fat interface (ISP anti-pattern: fat interface forces clients to depend on unused methods — see `Worker`/`MultiFunction` printer fat-interface literature; clients needing only pure `map` for headless tests would still depend on cache invalidation; NDepend ISP, Baeldung ISP, code-note-vr ISP). Per ISP (Robert C. Martin: "No client should be forced to depend on methods it does not use") the cache concern is segregated: `IMapper<AppT,ReT>` holds only pure `map(AppT, Ctx) → ReT`; `ICachedMapper<AppT,ReT> : public IMapper<AppT,ReT>` adds `mapCached` + `invalidate`. `Broker` stores `ICachedMapper` for stateful mappers but exposes `IMapper` to callers that only translate. The cache decorator is closed for modification (OCP) — a non-cached mapper (e.g., stateless `PlaneMapper`) implements only `IMapper`. **Header decision (resolves §13 Q33):** `i_mapper.hpp` declares `IMapper` + `ICachedMapper` together (single header, ISP-segregated by inheritance) for include simplicity; separate `i_cached_mapper.hpp` is retained as *alias include* (`#include "i_mapper.hpp"`) so `app/` DIP graph stays stable. `IViewBridge` is segregated into `ISyncBridge{sync}` + `IRenderBridge{renderAll,presentAll}` with `IViewBridge : ISyncBridge, IRenderBridge` (composition) — headless `tests_sync_only` includes only `i_sync_bridge.hpp` (ISP; DIP for test double).

**SOLID 11.2.2 — DIP ownership (research-backed, web-verified):** Per DIP, high-level policy (`scene/` + `broker/` orchestration) must own abstractions; low-level details (`render/` concrete `Re*Object`, `core/` GL) depend on them, not the reverse (Oleksii Tymoshchenko 2026-01-15: "policy owns interface, detail implements"; Baeldung DIP "who owns abstraction matters"; DIP checklist). `IMapper`/`IViewBridge`/`TranslateContext` interfaces are therefore declared in `broker/` (policy layer) and **owned by `broker/`**, not by `render/` or `scene/`. `render/` provides concrete `Re*` types via factory/adapter that implement `broker/`-owned concepts (e.g., `RenderableHandle` concept), and `scene/` provides `App*` value types that satisfy `broker/` input concepts. `app/` depends only on `IViewBridge` + `scene/` types — never on `render/` or `core/` concretions. **Broker ↔ render ACL (anti-corruption layer, binding):** `broker/` is the *only* library that may include both `scene/` and `render/` concrete headers (allowed per §3/§11). Its dependency on concrete `ReMeshObject` names for `IMapper<AppT,ReT>` instantiation is an ACL — the stable abstraction (`IMapper` contract + `Broker::registerMapper` factory) lives in `broker/`; `render/` types satisfy the concept but `render/` never depends on `broker/` internals beyond the concept. Concrete wiring is at composition root `AppContext{SceneStore, Broker, ViewBridge}` (DIP composition root). Pure inversion (broker defines opaque `RenderableHandle` handle, render maps handle) is deferred to IRHI migration where `IRHIFramebuffer/IRHITexture` opaque handles replace `Re*Object` concrete (see EOL-1).

**SOLID 11.3.1 — SRP (research-backed, web-verified):** The prior `ViewBridge{sync, renderAll, presentAll}` was a Facade with three reasons to change (sync/caching policy, render dispatch, present/blit backend) — the classic Facade-SRP tension (StackOverflow 39079694: "Facade as Wrapper via Composition and Encapsulation" — SRP violated when Facade does Transaction/Logging/ErrorHandling beyond delegation; ICS SRP 2024-08-14: "one actor, one reason to change" — different teams requesting sync vs present changes = two actors). Per SRP ("a module should be responsible to one actor" — Martin Clean Architecture Ch.7), the responsibilities are split into two single-responsibility collaborators (`ViewSynchronizer`: persistence/caching+CompositeKey; actor: persistence team; `ViewCompositor`: render dispatch/present+ReView map; actor: composition team). `ViewBridge` itself is a *coordinator* owning no state beyond the two collaborators — its single responsibility is *orchestration* (actor: workflow team), and it changes only when the coordination workflow changes (see Evertop SRP). Similarly, `ViewMapper` is documented as an *orchestrator* that delegates to per-field mappers; its single responsibility is "assemble `ReView` from translated fields" — it holds `Broker::get<T>()` refs, not caches (cache lives in `ViewSynchronizer` + `ICachedMapper` — SRP cache ownership clarified: `Broker` holds mapper *registry* `type_index→IMapper`, `ViewSynchronizer` holds generation/contentHash *cache* `CompositeKey→ReView`; Broker does not hold per-field gen). `ReView`'s FBO lifecycle is delegated to `ViewTarget{IRHIFramebuffer}` (SRP via composition) to avoid `ReView` becoming a God object; remaining `ReView` fields (rect+camera+plane+lights+items) are one actor (view composition) not three — lights vs camera vs items are *not* separate actors here because they are all "view composition" requested by the same layout actor (one View per screen section). God-object guard: `SceneStore` kept as single aggregate root per DDD bounded context (one team owns scene identity), not split into HandleRegistry+GenTracker+HashCache which would increase indirection without actor separation (DDD bounded context, Software Patterns Lexicon; God Object anti-pattern dilankam 2024).

**SOLID 11.3.2 — OCP (research-backed, Point of Variation, variant vs hierarchy trade-off — web-verified):** OCP (Meyer 1988: "open for extension, closed for modification"; PV principle: "Identify points of predicted variation and create a stable interface around them" — NDepend OCP) requires that adding a new `AppT`/`ReT` (e.g., `PointCloudObject`, `AreaLight`, `ToonMaterial`) needs **zero** modification to existing mapper files or to `ViewMapper`. This is achieved by (a) `Broker` keyed by `std::type_index(typeid(AppT))` with factory registration (`registerMapper`) — no central `enum AppObjectKind` switch (enum violates OCP; adding a kind edits enum+switches — Meyer PV, ICS OCP). `type_index` factory keeps `Broker` closed for modification, open for extension via `registerMapper` (one registration line per new type). RTTI coupling bounded (compile-time `typeid` of complete type). (b) `MaterialDesc`/`LightDesc`/`ReLight` use `std::variant` + `std::visit` visitor overload sets — new alternative adds a new `*Mapper` file implementing `IMapper<NewDesc,NewRe>` plus one overload in the visitor; `ViewMapper` is not edited because it iterates `items` and resolves mappers via `Broker::get<AppT>` generically. **Variant vs polymorphic hierarchy OCP trade-off (binding, web-verified):** `std::variant` is *open for adding operations* (new visitor) but *closed for adding types* (variant type list edit — Here Be Braces 2020-06-26; StackOverflow variant vs virtuals; Nordvarg 2025 variant+visit). Polymorphic hierarchy is opposite: open for types, closed for operations. V3 chooses *variant* because the *type set is closed/small* (`IMaterial` 4, `ILight` 3, bounded per SPEC §1 Phong-only non-goal) and *operations* vary more (shading, culling, TF, pipeline). Adding `ToonMaterial` edits one variant alias + one visitor overload (one file edit) but zero edits to existing concrete mapper files; `Broker::registerMapper` keeps `ViewMapper` closed. A future EOL with many material kinds can migrate to polymorphic `IMaterial` open hierarchy without touching `ViewMapper` (OCP via factory). The visitor `std::visit(overloaded{...})` handles both paths — value-hash vs `MaterialId` — OCP via overload set.

**SOLID 11.3.3 — Dependency / Ownership (DIP):** `Broker` owns `type_index → unique_ptr<IMapperBase>` (one `MaterialMapper` dedup cache, shared lights, etc. — lazy per-`scene::View` creation would fragment dedup caches; owned-once guarantees one cache per type).

### 11.4 Contextual rule — `View` owns the plane, not the item

- `scene::MeshSliceObject` / `scene::VolumeSliceObject` **do not** carry a plane field;
  `scene::View::plane` is the source of truth for all `2D` views (`plane
  present → 2D`, `nullopt → 3D`). Their mappers therefore need a
  `TranslateContext{ const ClipPlane* viewPlane }` second arg (or `ViewMapper`
  bakes the translated `ClipPlane` into a context struct threaded through
  `ViewMapper → *SliceObjectMapper`). A `MeshSlice` needing a plane independent
  of its `View` must carry an explicit `optional<scene::PlaneDesc> override`
  — conflict (`View plane` vs `item override`) is a typed error on `ViewMapper`.

**SOLID 11.4.1 — ISP / LSP for context (web-verified, binding patch):** `TranslateContext` is a *cohesive* minimal struct for slice mapping, but to avoid fat-context ISP violation it is composed of two role structs (ISP: no client forced to depend on unused members — NDepend ISP). `struct TranslateContext { ViewContext view; std::optional<VolumeContext> volume; }` where `ViewContext{ const ClipPlane* viewPlane; glm::mat4 viewMatrix; glm::mat4 projMatrix; }` is needed by every mapper, and `VolumeContext{ glm::mat4 volumeModel; glm::ivec3 dims; float voxelSpacing; Aabb meshBounds; }` is only where `Space::VoxelIndex→world` conversion is needed (`PlaneMapper`, `VolumeSliceObjectMapper`). Mappers take `const TranslateContext&` but touch only their role; `CameraMapper` touches only `view`, not `volume`; `PlaneMapper` touches `volume` for voxel→world math but not `viewPlane` when `hasPlane()==false`. Per ISP, `PlaneMapper` depending on full `ReView` would be forced to depend on lights/items it never uses — segregated contexts fix this; per LSP, a `TranslateContext` with `volume==nullopt` and `viewPlane==nullptr` is a valid substitute for 3D mappers (they ignore volume/plane) without throwing `UnsupportedOperation` — predicate `hasPlane()`/`hasVolume()` keeps preconditions weak (LSP preconditions cannot be strengthened). `IMapper::map` signature is uniform (`map(const AppT&, const TranslateContext&)`) so all mappers are substitutable (LSP) regardless of whether they read the optional role; context construction is `ViewMapper`'s single responsibility (SRP orchestrator). Future `Space::NormalizedDevice` adds `SpaceConverter` extension consuming `TranslateContext`, not scatter (OCP).

### 11.5 Build / ownership / guardrail

- `scene/` links to `data`, `volume`, `glm` + `data/result`.
- `broker/` links to `scene/`, `render/`, `core/`-wrappers (never raw `gl*`);
  CMake target `re_broker` is a `STATIC` lib alongside `re_scene`,
  `re_core`, `re_render`.
- Audit: `forbid_outside core|\bgl[A-Z]` holds — `broker/` is **outside**
  `core/` so any raw `gl*(` in `broker/` would fail the audit. Broker
  upload paths (e.g., `MeshObjectMapper` creating `AssetHandle`) forward
  through `render/AssetRegistry`/`ReMeshObject` helpers; they never call
  `glTexImage` directly. Add `broker/` to `AUDIT_SOURCE_DIRS` via
  `tools/env.sh` / `AGENTS.md`.
